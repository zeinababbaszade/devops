ARP چیست و چرا به آن نیاز داریم؟

ARP مخفف Address Resolution Protocol است. در شبکه‌های IPv4، سیستم‌ها برای ارتباط از IP Address استفاده می‌کنند، اما در شبکه Ethernet، ارسال Frame در Layer 2 بر اساس MAC Address انجام می‌شود. بنابراین سیستم باید بتواند بفهمد:

اگر IP مقصد را دارم، MAC Address مربوط به آن چیست؟

اینجاست که ARP وارد عمل می‌شود. فرض کنید کامپیوتر ما دارای IP زیر است:

Example 
192.168.1.10

و می‌خواهیم با سیستم دیگری با IP زیر ارتباط برقرار کنیم:

Destination 
192.168.1.20

اگر مقصد در همان شبکه Local باشد، سیستم باید MAC مربوط به 192.168.1.20 را پیدا کند تا بتواند Ethernet Frame را ارسال کند. ARP دقیقاً برای همین Mapping استفاده می‌شود:

Concept 
IPv4 Address
     ↓
    ARP
     ↓
MAC Address

رابطه IP و MAC

یکی از مهم‌ترین مفاهیمی که در Networking باید یاد بگیریم تفاوت بین IP Address و MAC Address است. IP در Layer 3 قرار دارد و برای Addressing منطقی و Routing استفاده می‌شود. MAC در Layer 2 قرار دارد و برای انتقال Frame در شبکه محلی Ethernet استفاده می‌شود.

ویژگی IP Address MAC Address
Layer Layer 3 Layer 2
کاربرد Addressing و Routing انتقال Local Frame
مثال 192.168.1.10 00:1A:2B:3C:4D:5E
تغییرپذیری ممکن است تغییر کند معمولاً به Interface مرتبط است
نکته مهم: ARP نمی‌گوید «این IP متعلق به این کامپیوتر در کل اینترنت است». ARP فقط برای پیدا کردن ارتباط بین IPv4 و MAC در Local Network / Broadcast Domain استفاده می‌شود.

ARP Request

فرض کنید سیستم ما می‌خواهد به 192.168.1.20 دسترسی پیدا کند، اما MAC مقصد را در Cache ندارد. سیستم یک ARP Request تولید می‌کند. مفهوم پیام تقریباً این است:

Who has 192.168.1.20? Tell 192.168.1.10

از آنجا که سیستم هنوز MAC مقصد را نمی‌داند، Request باید به صورت Broadcast ارسال شود. MAC مقصد Broadcast در Ethernet:

Broadcast MAC 
ff:ff:ff:ff:ff:ff

بنابراین تمام سیستم‌های موجود در همان Broadcast Domain می‌توانند ARP Request را دریافت کنند. اما فقط سیستمی که مالک IP موردنظر است باید پاسخ مناسب بدهد.

ARP Reply

سیستم دارای IP 192.168.1.20 ARP Request را دریافت می‌کند. اگر IP متعلق به خودش باشد، یک ARP Reply ارسال می‌کند. برای مثال:

ARP Reply 
192.168.1.20 is at
00:11:22:33:44:55

سیستم مبدأ حالا می‌داند:

Mapping 
192.168.1.20
        ↓
00:11:22:33:44:55

و می‌تواند Ethernet Frame را به MAC مقصد ارسال کند.

ARP Cache چیست؟

اگر سیستم برای هر Packet دوباره ARP Request ارسال کند، تعداد Broadcastها بسیار زیاد خواهد شد. به همین دلیل سیستم‌عامل نتیجه ARP را برای مدتی در یک جدول نگهداری می‌کند که به آن: ARP Cache یا در Linux مدرن: Neighbor Table گفته می‌شود.

در Linux می‌توانیم این جدول را مشاهده کنیم:

Ubuntu / Linux 
ip neigh

ممکن است چیزی شبیه این ببینید:

Example Output 
192.168.1.1 dev ens33 lladdr 00:11:22:33:44:55 REACHABLE

192.168.1.20 dev ens33 lladdr aa:bb:cc:dd:ee:ff STALE

در این خروجی:

  • 192.168.1.1 آدرس IP مقصد است.
  • dev ens33 Interface مورد استفاده است.
  • lladdr MAC Address مقصد است.
  • REACHABLE نشان می‌دهد Neighbor اخیراً قابل دسترس بوده است.
  • STALE یعنی اطلاعات وجود دارد ولی تازگی آن تضمین نشده است.
نکته DevOps: وقتی یک Server نمی‌تواند با Gateway یا Server دیگری ارتباط برقرار کند، بررسی ip neigh یکی از تست‌های سریع و مفید است.

ARP و Default Gateway

این قسمت یکی از مهم‌ترین کاربردهای ARP است. فرض کنید Server ما:

Server 
IP:      192.168.1.10
Mask:    255.255.255.0
Gateway: 192.168.1.1

حالا می‌خواهیم به این IP دسترسی پیدا کنیم:

Remote Server 
8.8.8.8

این مقصد خارج از Subnet ماست. در این حالت Server نمی‌رود MAC مربوط به 8.8.8.8 را پیدا کند. بلکه MAC مربوط به Default Gateway را پیدا می‌کند.

Concept 
8.8.8.8
   ↓
Routing Table
   ↓
Default Gateway
   ↓
192.168.1.1
   ↓
ARP
   ↓
Gateway MAC
   ↓
Ethernet Frame
اشتباه رایج: برای ارتباط با یک Server خارج از شبکه Local، لازم نیست MAC آن Server را بدانیم. MAC فقط برای Link فعلی اهمیت دارد. Router در هر Hop، Frame جدیدی ایجاد می‌کند.

ARP و Subnet

ARP فقط در همان Local Network معنا دارد. فرض کنید سیستم ما:

Host 
IP: 192.168.10.50
Mask: 255.255.255.0

و مقصد:

Destination 
192.168.10.100

هر دو در:

Network 
192.168.10.0/24

قرار دارند. پس Host می‌تواند مستقیماً برای IP مقصد ARP انجام دهد. اما اگر مقصد:

Remote Network 
192.168.20.100

باشد، سیستم باید Routing Table را بررسی کند و معمولاً Packet را به Gateway بفرستد.

ARP در Linux

در Linux ابزار مدرن برای مشاهده Neighbor Table دستور ip neigh است. برای مشاهده:

Linux 
ip neigh show

برای Interface خاص:

Linux 
ip neigh show dev eth0

برای مشاهده Interfaceها:

Linux 
ip link

برای مشاهده IP:

Linux 
ip addr

و برای مشاهده Routing:

Linux 
ip route

این سه دستور را کنار هم استفاده کنید:

Network Troubleshooting 
ip addr
ip route
ip neigh

به این ترتیب می‌توانیم بفهمیم:

  • Interface ما چه IPای دارد؟
  • Subnet ما چیست؟
  • Default Gateway کدام است؟
  • آیا MAC مربوط به Gateway در Neighbor Table وجود دارد؟
  • وضعیت Neighbor چیست؟

Gratuitous ARP چیست؟

Gratuitous ARP یا GARP حالتی است که یک سیستم بدون اینکه الزاماً منتظر ARP Request باشد، اطلاعات مربوط به IP/MAC خود را روی شبکه اعلام می‌کند. این کار می‌تواند کاربردهای مختلفی داشته باشد.

  • اطلاع دادن تغییر MAC برای یک IP
  • High Availability
  • Failover
  • به‌روزرسانی Cache سیستم‌های دیگر
  • تشخیص Duplicate IP در برخی سناریوها

برای مثال در یک Cluster ممکن است Virtual IP از یک Node به Node دیگر منتقل شود. Node جدید می‌تواند با ارسال GARP باعث شود سیستم‌های شبکه سریع‌تر Mapping جدید را یاد بگیرند.

کاربرد DevOps: در معماری‌های High Availability، Load Balancing و Failover، درک GARP می‌تواند برای Troubleshooting تغییر ناگهانی مسیر یا MAC بسیار مفید باشد.

Proxy ARP

در حالت معمول یک Host فقط برای مقصدهای Local ARP انجام می‌دهد. اما در برخی معماری‌ها Router می‌تواند به جای Host دیگر به ARP Request پاسخ دهد. به این قابلیت: Proxy ARP گفته می‌شود.

یعنی یک Router ممکن است بگوید:

«برای این IP، MAC من را استفاده کن؛ من Packet را به مقصد واقعی Forward می‌کنم.»

Proxy ARP در شبکه‌های خاص و برخی معماری‌های Legacy یا پیچیده استفاده می‌شود، اما برای طراحی‌های مدرن باید با درک کامل از Routing و Security استفاده شود.

ARP Spoofing و امنیت

ARP ذاتاً یک مکانیزم احراز هویت قوی ندارد. به همین دلیل در شبکه‌های Local، حملاتی مانند: ARP Spoofing یا ARP Poisoning ممکن است رخ دهند.

در یک سناریوی ساده، مهاجم می‌تواند تلاش کند سیستم‌ها را متقاعد کند که:

Fake Mapping 
192.168.1.1
      ↓
Attacker MAC

در نتیجه ممکن است Traffic از مسیر مهاجم عبور کند. این موضوع می‌تواند زمینه‌ساز حملاتی مانند Man-in-the-Middle باشد.

نکته امنیتی: ARP Spoofing را فقط در Lab یا محیطی که مجوز تست دارید بررسی کنید. در شبکه واقعی، بررسی ARP غیرعادی باید با ابزارهای Monitoring و Security انجام شود.

برای مشاهده Mappingهای فعلی در Linux:

Linux 
ip neigh

اگر MAC مربوط به Gateway بدون دلیل تغییر کند، می‌تواند یکی از مواردی باشد که در Troubleshooting امنیتی بررسی می‌شود؛ البته تغییر MAC به تنهایی اثبات حمله نیست.

Troubleshooting با tcpdump

یکی از بهترین روش‌ها برای فهم واقعی ARP، مشاهده Packetهای آن است. ابزار tcpdump در Linux برای Packet Capture بسیار کاربردی است. ابتدا Interface را پیدا کنید:

Linux 
ip link

فرض کنیم Interface ما eth0 است. برای مشاهده ARP:

tcpdump 
sudo tcpdump -i eth0 arp

حالا یک Host موجود در شبکه را Ping کنید.

Linux 
ping -c 3 192.168.1.1

اگر MAC مربوط به Gateway در Cache وجود نداشته باشد، ممکن است ابتدا ARP Request را ببینید و سپس ARP Reply. این کار باعث می‌شود چیزی که در تئوری خوانده‌ایم را به صورت واقعی داخل Packet Capture ببینیم.

روش حرفه‌ای Troubleshooting: به جای اینکه فقط بگوییم «شبکه قطع است»، مرحله‌به‌مرحله بررسی کنیم: Interface → IP → Route → ARP/Neighbor → ICMP → TCP → Application

ARP و Docker

در محیط‌های DevOps، Networking فقط به Serverهای فیزیکی محدود نیست. Docker نیز Networking را به شکل Virtual انجام می‌دهد. برای مثال در Docker معمولاً Networkهایی مانند Bridge وجود دارند.

Docker 
docker network ls

برای مشاهده جزئیات یک Network:

Docker 
docker network inspect bridge

درک ARP و Layer 2 کمک می‌کند بفهمیم Containerها چگونه در یک شبکه مجازی با یکدیگر ارتباط برقرار می‌کنند و Docker چگونه Traffic را از طریق Interfaceها و Bridgeهای Linux عبور می‌دهد.

ارتباط با DevOps: اگر ARP، MAC، IP، Routing و Interface را درست درک کنید، یادگیری Docker Networking، Kubernetes Networking، CNI و Cloud Networking بسیار ساده‌تر می‌شود.

🧪 Lab عملی کامل

مرحله ۱ — اطلاعات شبکه سیستم

ابتدا Interfaceها و IPهای سیستم خود را بررسی کنید.

Ubuntu 
ip addr

حالا Routing Table را ببینید:

Ubuntu 
ip route

مرحله ۲ — مشاهده Neighbor Table

حالا وضعیت ARP/Neighbor سیستم را بررسی کنید:

Ubuntu 
ip neigh

به دنبال IP مربوط به Default Gateway بگردید. اگر قبلاً با Gateway ارتباط داشته باشید، احتمالاً Mapping مربوط به آن را مشاهده خواهید کرد.

مرحله ۳ — تولید ARP Traffic

ابتدا Cache را مشاهده کنید:

Ubuntu 
ip neigh

سپس Gateway را از Routing Table پیدا کنید:

Ubuntu 
ip route

حالا Gateway را Ping کنید:

Ubuntu 
ping -c 4 <GATEWAY-IP>

دوباره Neighbor Table را بررسی کنید:

Ubuntu 
ip neigh

بررسی کنید آیا وضعیت Neighbor تغییر کرده است یا خیر.

مرحله ۴ — مشاهده ARP با tcpdump

یک Terminal باز کنید و Capture را شروع کنید:

Terminal 1 
sudo tcpdump -i <INTERFACE> -n arp

در Terminal دوم Gateway را Ping کنید:

Terminal 2 
ping -c 3 <GATEWAY-IP>

هدف این تمرین این است که ARP Request و Reply را در Packet Capture مشاهده کنید.

مرحله ۵ — بررسی ارتباط کامل

بعد از بررسی ARP، مسیر ارتباط را تا لایه‌های بالاتر دنبال کنید:

Linux 
ip addr
ip route
ip neigh
ping -c 4 1.1.1.1
ss -lntup
curl -v https://example.com

در هر مرحله مشخص کنید مشکل احتمالی در کدام Layer قرار دارد.

دستور کاربرد

🎯 چه چیزی یاد گرفتیم؟

  • ARP وظیفه پیدا کردن MAC مربوط به IPv4 در Local Network را بر عهده دارد.
  • ARP Request معمولاً به صورت Broadcast ارسال می‌شود.
  • ARP Reply اطلاعات MAC مقصد را در اختیار Host قرار می‌دهد.
  • Linux اطلاعات Neighbor را در جدول Neighbor نگهداری می‌کند.
  • دستور ip neigh ابزار اصلی بررسی این اطلاعات در Linux است.
  • برای مقصدهای خارج از Subnet، Host معمولاً MAC مربوط به Default Gateway را پیدا می‌کند.
  • Gratuitous ARP در برخی سناریوهای Failover و High Availability کاربرد دارد.
  • Proxy ARP می‌تواند باعث پاسخ Router به ARP Request شود.
  • ARP از نظر امنیتی دارای محدودیت‌هایی است و ARP Spoofing یکی از تهدیدهای شناخته‌شده آن است.
  • با tcpdump می‌توان ARP را به صورت واقعی در Packet Capture مشاهده کرد.
  • درک ARP پایه مهمی برای یادگیری Docker Networking، Kubernetes و Cloud Networking است.
نکته مهم برای مسیر DevOps: ARP را فقط به عنوان یک پروتکل حفظ نکنید. سعی کنید همیشه ارتباط این مفاهیم را در ذهن داشته باشید:
DevOps Networking Mental Model 
Application
     ↓
TCP / UDP
     ↓
IP / Routing
     ↓
ARP / Neighbor Discovery
     ↓
MAC / Ethernet
     ↓
Network Interface
     ↓
Physical / Virtual Network

وقتی یک سرویس در محیط Production در دسترس نیست، داشتن همین مدل ذهنی باعث می‌شود به جای حدس زدن، مشکل را مرحله‌به‌مرحله پیدا کنید.

تمرین پیشنهادی: در Ubuntu خود یک سناریوی ساده طراحی کنید: یک Server، یک Gateway و یک مقصد دیگر. سپس با استفاده از: ip addr، ip route، ip neigh و tcpdump مسیر Packet را از لحظه‌ای که Application درخواست را ایجاد می‌کند تا رسیدن آن به Gateway بررسی کنید. این تمرین یکی از بهترین راه‌ها برای تثبیت مفاهیم Layer 2 و Layer 3 است.
