TCP/IP Model چیست؟

TCP/IP Model مدلی برای درک نحوه ارتباط سیستم‌ها در شبکه است. برخلاف تصور رایج، TCP/IP فقط نام دو پروتکل TCP و IP نیست؛ بلکه مجموعه بزرگی از پروتکل‌ها و استانداردهایی است که در کنار یکدیگر ارتباطات شبکه‌ای را ایجاد می‌کنند.

وقتی یک کامپیوتر Linux به یک Server متصل می‌شود، اتفاقات زیادی پشت سر هم رخ می‌دهد: سیستم باید Interface مناسب را پیدا کند، مقصد را مشخص کند، Routing را بررسی کند، Packet را بسازد، ارتباط Transport ایجاد کند و در نهایت Application بتواند داده موردنظر خود را دریافت کند.

TCP/IP Model این فرآیند پیچیده را به چند بخش منطقی تقسیم می‌کند تا بتوانیم شبکه را راحت‌تر طراحی، پیاده‌سازی و Troubleshoot کنیم.

نکته مهم: TCP/IP را بهتر است فقط به عنوان یک مدل حفظ نکنید. هدف اصلی این است که وقتی مثلاً curl https://example.com شکست خورد، بتوانید تشخیص دهید مشکل در کدام بخش از مسیر ارتباط قرار دارد.

TCP/IP Model در دنیای واقعی

مدل چهارلایه‌ای رایج TCP/IP شامل چهار بخش است:

Layer نام وظیفه نمونه‌ها
1 Link ارتباط در شبکه محلی Ethernet, Wi-Fi, ARP
2 Internet Addressing و Routing بین شبکه‌ها IPv4, IPv6, ICMP
3 Transport ارتباط Process-to-Process TCP, UDP
4 Application سرویس‌ها و پروتکل‌های کاربردی HTTP, DNS, SSH, SMTP

عددگذاری بالا از 1 تا 4 است و نباید آن را با شماره‌گذاری OSI اشتباه گرفت. مهم‌تر از شماره لایه، وظیفه‌ای است که هر بخش انجام می‌دهد.

Layer 1 — Link

در مدل چهارلایه‌ای TCP/IP، Link مسئول ارتباط روی شبکه محلی یا Local Network است.

برای مثال وقتی یک Linux Server از طریق Ethernet به Switch متصل است، انتقال Frameها در همین محدوده انجام می‌شود.

مفاهیم مهم Link Layer

  • Ethernet
  • Wi-Fi
  • MAC Address
  • Ethernet Frame
  • Network Interface
  • Switch
  • ARP در ارتباط IPv4 و شبکه محلی

MAC Address چیست؟

MAC Address شناسه‌ای است که در ارتباطات Link Layer برای شناسایی Interface در شبکه محلی استفاده می‌شود.

در Linux می‌توانید Interfaceها و MAC Addressهای آن‌ها را مشاهده کنید:

Ubuntu 
ip link

برای مشاهده جزئیات Interface:

Ubuntu 
ip addr show

اگر Link Layer مشکل داشته باشد چه می‌شود؟

اگر Interface شما Down باشد یا اتصال فیزیکی برقرار نباشد، حتی اگر IP و DNS کاملاً درست باشند، ارتباط شبکه‌ای انجام نمی‌شود.

برای بررسی وضعیت Interface:

Ubuntu 
ip link show
در Troubleshooting: اگر Interface اصلاً UP نیست، بررسی DNS یا HTTP معمولاً زود است. ابتدا باید مطمئن شوید Interface و Link وضعیت مناسبی دارند.

Layer 2 — Internet

Internet Layer مسئول Addressing منطقی و انتقال Packet بین شبکه‌های مختلف است.

مهم‌ترین مفهوم این بخش IP است.

IPv4

IPv4 از Addressهای 32 بیتی استفاده می‌کند؛ مانند:

Example 
192.168.1.10

IPv6

IPv6 برای فضای بسیار بزرگ‌تر Addressing طراحی شده و از Addressهای 128 بیتی استفاده می‌کند.

Example 
2001:db8::10

Routing چه نقشی دارد؟

اگر مقصد در همان شبکه محلی نباشد، سیستم باید تصمیم بگیرد Packet را به کجا ارسال کند. این تصمیم از طریق Routing Table انجام می‌شود.

Ubuntu 
ip route

یک Routing Table ممکن است چیزی شبیه این باشد:

Example 
default via 192.168.1.1 dev ens33
192.168.1.0/24 dev ens33 proto kernel scope link src 192.168.1.20

خط اول Default Route را نشان می‌دهد. یعنی برای مقصدهایی که Route مشخص‌تری وجود ندارد، Packet به Gateway ارسال می‌شود.

ICMP

ICMP نیز در Internet Layer استفاده می‌شود و ابزارهایی مانند ping برای تست Reachability از آن استفاده می‌کنند.

Ubuntu 
ping -c 4 8.8.8.8
نکته: موفق بودن Ping به این معنی نیست که تمام سرویس‌ها سالم هستند. ممکن است ICMP مجاز باشد اما TCP روی Port موردنظر توسط Firewall مسدود شده باشد.

Layer 3 — Transport

Transport Layer ارتباط را بین Processها برقرار می‌کند. دو پروتکل مهم این بخش TCP و UDP هستند.

TCP

TCP یک پروتکل Connection-Oriented است. قبل از انتقال معمول داده، دو طرف یک ارتباط منطقی برقرار می‌کنند.

TCP قابلیت‌هایی مانند موارد زیر را فراهم می‌کند:

  • Reliable Delivery
  • Ordering
  • Retransmission
  • Flow Control
  • Congestion Control

TCP Three-Way Handshake

برقراری اتصال TCP معمولاً با یک Handshake سه‌مرحله‌ای انجام می‌شود:

  1. Client یک SYN ارسال می‌کند.
  2. Server یک SYN-ACK ارسال می‌کند.
  3. Client یک ACK ارسال می‌کند.
Concept 
Client                 Server

   SYN ------------------>

       <------------------ SYN-ACK

   ACK ------------------>

       Connection Established

UDP

UDP برخلاف TCP اتصال و Reliability داخلی مشابه TCP ارائه نمی‌کند و Header ساده‌تری دارد.

UDP در سناریوهایی که سربار کمتر یا رفتار Datagram-based مناسب است کاربرد دارد؛ برای مثال DNS و بسیاری از پروتکل‌های Real-Time می‌توانند از UDP استفاده کنند.

Port چیست؟

IP مشخص می‌کند Packet به کدام Host برسد، اما Port مشخص می‌کند داده برای کدام Service یا Process در آن Host است.

برای مثال:

Example 
192.168.1.20:22
192.168.1.20:80
192.168.1.20:443

در این مثال Host یکی است اما Service می‌تواند متفاوت باشد.

Layer 4 — Application

Application Layer جایی است که پروتکل‌هایی قرار می‌گیرند که سرویس‌های واقعی شبکه را در اختیار Applicationها قرار می‌دهند.

Protocol کاربرد Port رایج
HTTP Web 80
HTTPS Secure Web 443
SSH Remote Administration 22
DNS Name Resolution 53
SMTP Email 25 / 587

HTTP

HTTP پروتکلی است که Client و Web Server از طریق آن Request و Response ردوبدل می‌کنند.

Ubuntu 
curl -I https://example.com

DNS

DNS نام‌هایی مانند example.com را به Addressهای IP تبدیل می‌کند.

Ubuntu 
dig example.com

SSH

SSH یک پروتکل مهم برای مدیریت Remote Serverها است و در کار روزمره DevOps نقش بسیار مهمی دارد.

Ubuntu 
ssh user@192.168.1.20

Encapsulation و Decapsulation

یکی از مهم‌ترین مفاهیم TCP/IP، Encapsulation است.

وقتی Application داده‌ای ایجاد می‌کند، داده در مسیر عبور از لایه‌ها اطلاعات مربوط به همان لایه را دریافت می‌کند.

Concept 
Application Data
       ↓
Transport Segment
       ↓
IP Packet
       ↓
Ethernet Frame
       ↓
Bits on the Network

در مقصد این فرآیند برعکس می‌شود و سیستم اطلاعات مربوط به هر لایه را باز می‌کند. این فرآیند Decapsulation نام دارد.

نام Data در هر مرحله

Layer واحد رایج داده
Application Data / Message
Transport TCP Segment / UDP Datagram
Internet IP Packet
Link Frame

IP، MAC و Port چه تفاوتی دارند؟

این سه مفهوم را باید کاملاً از هم جدا کنید؛ زیرا در Troubleshooting دائماً با آن‌ها مواجه خواهید شد.

مفهوم مثال نقش
MAC 00:11:22:33:44:55 شناسایی Interface در شبکه محلی
IP 192.168.1.20 شناسایی منطقی Host و Routing
Port 443 شناسایی Service/Process

بنابراین وقتی می‌گوییم:

Example 
192.168.1.20:443

قسمت اول IP Address مربوط به Host است و قسمت دوم Port مربوط به Service است.

مدل ذهنی ساده: MAC را برای ارتباط محلی، IP را برای پیدا کردن Host و Port را برای پیدا کردن Service در نظر بگیرید.

TCP/IP در یک درخواست واقعی HTTPS

حالا فرض کنید روی Linux این دستور را اجرا می‌کنیم:

Ubuntu 
curl https://example.com

برای انجام این درخواست چند مرحله پشت سر هم اتفاق می‌افتد.

مرحله 1 — DNS

سیستم باید بفهمد example.com به چه IP Addressهایی Resolve می‌شود.

Ubuntu 
dig example.com

مرحله 2 — Routing

سیستم بررسی می‌کند Packet برای رسیدن به مقصد باید از کدام Interface و Gateway عبور کند.

Ubuntu 
ip route get 93.184.216.34

مرحله 3 — TCP

برای HTTPS معمولاً یک TCP Connection به Port 443 ایجاد می‌شود.

مرحله 4 — TLS

در HTTPS، بعد از ایجاد Transport Connection، TLS برای ایجاد ارتباط رمزنگاری‌شده استفاده می‌شود.

مرحله 5 — HTTP

در نهایت HTTP Request ارسال می‌شود و Server Response برمی‌گرداند.

Concept 
DNS
 ↓
IP / Routing
 ↓
TCP Connection
 ↓
TLS
 ↓
HTTP Request
 ↓
HTTP Response

این زنجیره یکی از مهم‌ترین مدل‌های ذهنی برای Troubleshooting سرویس‌های Web است.

TCP/IP در Linux

Linux ابزارهای بسیار قدرتمندی برای مشاهده وضعیت شبکه در اختیار ما قرار می‌دهد.

مشاهده Interface

Ubuntu 
ip addr
ip link

مشاهده Routing

Ubuntu 
ip route
ip route get 8.8.8.8

مشاهده Socketها

Ubuntu 
ss -lntup

این دستور به شما کمک می‌کند بفهمید چه Serviceهایی در حال Listening هستند.

بررسی Connectivity

Ubuntu 
ping -c 4 8.8.8.8

بررسی DNS

Ubuntu 
dig example.com

بررسی HTTP/TLS

Ubuntu 
curl -v https://example.com

TCP/IP و DNS

DNS یکی از بخش‌هایی است که در Troubleshooting شبکه بسیار مهم است؛ زیرا بسیاری از خطاهایی که کاربر به صورت «سایت باز نمی‌شود» می‌بیند، ممکن است در واقع مربوط به Name Resolution باشند.

برای مثال:

Ubuntu 
curl https://example.com

اگر DNS کار نکند ممکن است سیستم اصلاً نتواند نام Domain را به IP تبدیل کند.

برای تفکیک DNS از Connectivity می‌توانیم مستقیماً IP را تست کنیم:

Ubuntu 
ping -c 4 8.8.8.8
ping -c 4 example.com

این دو تست دقیقاً یکسان نیستند و تفاوت نتیجه آن‌ها می‌تواند سرنخ مهمی برای Troubleshooting ایجاد کند.

TCP/IP و Docker

در DevOps، Networking فقط مربوط به Serverهای فیزیکی یا Virtual Machineها نیست. Docker نیز از مفاهیم TCP/IP به‌شدت استفاده می‌کند.

هر Container می‌تواند Network Interface و IP Address مخصوص خود را داشته باشد و Docker برای ارتباط Containerها از Networkهای مختلف استفاده می‌کند.

مشاهده Networkهای Docker

Linux 
docker network ls

بررسی یک Network

Linux 
docker network inspect bridge

وقتی یک Application داخل Container روی Port خاصی Listening است، باید تفاوت بین Container Port و Host Port را نیز درک کنید.

Example 
docker run -p 8080:80 nginx

در این مثال، Port 80 داخل Container به Port 8080 روی Host Map شده است.

TCP/IP و Kubernetes

در Kubernetes نیز مفاهیم Networking اهمیت بسیار زیادی دارند.

Podها، Services، Cluster IP، DNS و Ingress همگی به Networking وابسته‌اند.

برای مثال اگر یک Pod بتواند به یک Service دسترسی نداشته باشد، باید بتوانیم بررسی کنیم مشکل در کدام قسمت قرار دارد:

  • Pod Network
  • IP Address
  • Routing
  • Service
  • DNS
  • Port
  • Network Policy
  • Application

بنابراین یادگیری TCP/IP پایه‌ای برای فهم Networking در Kubernetes است.

TCP/IP در Troubleshooting

یکی از کاربردهای اصلی TCP/IP Model برای DevOps، ایجاد یک روش منظم برای Troubleshooting است.

به جای اینکه بدون ترتیب چندین دستور اجرا کنیم، بهتر است ارتباط را مرحله‌به‌مرحله بررسی کنیم.

مرحله سؤال ابزار
Interface Interface فعال است؟ ip link
IP سیستم IP دارد؟ ip addr
Route مسیر مقصد مشخص است؟ ip route
Connectivity مقصد Reachable است؟ ping
DNS نام Resolve می‌شود؟ dig
Port Service Listening است؟ ss
Application سرویس پاسخ می‌دهد؟ curl
Packets Packet واقعاً عبور می‌کند؟ tcpdump

سناریوی واقعی Troubleshooting

فرض کنید کاربر گزارش داده است:

«سایت باز نمی‌شود.»

این جمله به تنهایی اطلاعات کافی ندارد. باید مرحله‌به‌مرحله بررسی کنیم.

مرحله اول — Interface

Ubuntu 
ip link

مرحله دوم — IP

Ubuntu 
ip addr

مرحله سوم — Gateway

Ubuntu 
ip route

مرحله چهارم — External Connectivity

Ubuntu 
ping -c 4 8.8.8.8

مرحله پنجم — DNS

Ubuntu 
dig example.com

مرحله ششم — TCP Port

Ubuntu 
nc -vz example.com 443

مرحله هفتم — HTTP/TLS

Ubuntu 
curl -v https://example.com

اگر همه این مراحل درست باشند ولی Application همچنان مشکل داشته باشد، بررسی باید به سمت Web Server، Reverse Proxy، Application، Authentication، Certificate و سایر اجزای سرویس ادامه پیدا کند.

روش DevOps: هدف Troubleshooting این نیست که فقط یک دستور خاص را بلد باشید؛ هدف این است که بتوانید یک مشکل پیچیده را به چند بخش کوچک‌تر تقسیم کنید و هر بخش را مستقل بررسی کنید.

🧪 Lab پیشرفته — مشاهده Packetها

برای مشاهده Packetهای واقعی می‌توانید از tcpdump استفاده کنید.

Ubuntu 
sudo tcpdump -i any -n

حالا در Terminal دیگری یک درخواست HTTP یا HTTPS ایجاد کنید:

Ubuntu 
curl -I https://example.com

در tcpdump می‌توانید Packetهایی را مشاهده کنید که در زمان اجرای درخواست از Interface عبور می‌کنند.

فیلتر TCP

Ubuntu 
sudo tcpdump -i any -n tcp

فیلتر Port 443

Ubuntu 
sudo tcpdump -i any -n port 443
توجه: برای اجرای tcpdump معمولاً به دسترسی مناسب مانند sudo نیاز دارید. Capture کردن Packetها در شبکه‌های واقعی نیز باید مطابق مجوزهای سازمان انجام شود.

TCP/IP و Monitoring

در محیط‌های DevOps و Monitoring، بسیاری از Metricها و Alertها مستقیماً یا غیرمستقیم با TCP/IP ارتباط دارند.

  • Packet Loss
  • Latency
  • TCP Connection Count
  • Connection Errors
  • Retransmission
  • Network Throughput
  • DNS Response Time
  • HTTP Response Time

برای مثال اگر یک Application در Grafana افزایش Latency نشان دهد، ممکن است علت در Application نباشد و Network Latency یا Packet Loss باعث افزایش زمان پاسخ شده باشد.

TCP/IP و DevOps

تقریباً تمام بخش‌های زیرساخت مدرن به Networking وابسته هستند:

  • Linux Servers
  • Virtual Machines
  • Docker
  • Kubernetes
  • Cloud
  • Load Balancer
  • Reverse Proxy
  • Monitoring
  • Logging
  • Databases
  • Message Brokers

بنابراین TCP/IP یکی از پایه‌های اصلی مسیر DevOps است. بدون درک آن، Troubleshooting سرویس‌های Distributed بسیار دشوار می‌شود.

  • رابطه TCP/IP با Docker و Kubernetes را بررسی کردیم.
  • یک روش مرحله‌ای برای Network Troubleshooting یاد گرفتیم.
  • با ابزارهایی مانند ip، ss، ping، dig، curl، nc و tcpdump کار کردیم.
نکته DevOps: TCP/IP را حفظ نکنید؛ آن را به یک مدل ذهنی تبدیل کنید. وقتی یک سرویس کار نمی‌کند، از خودتان بپرسید: Interface → IP → Route → Connectivity → DNS → Port → TCP/TLS → Application اگر بتوانید مشکل را به این مراحل تقسیم کنید، بسیاری از Incidentهای Networking که در Server، Docker، Cloud و Kubernetes با آن‌ها مواجه می‌شوید بسیار قابل فهم‌تر خواهند شد.

🎯 تمرین نهایی

روی Ubuntu خود یک سناریوی واقعی بسازید:

  1. با ip addr اطلاعات Interface و IP را پیدا کنید.
  2. با ip route Default Gateway را پیدا کنید.
  3. با ping یک مقصد IP را تست کنید.
  4. با dig یک Domain را Resolve کنید.
  5. با ss -lntup Portهای Listening را بررسی کنید.
  6. با nc یک Port را تست کنید.
  7. با curl -v یک HTTPS Connection ایجاد کنید.
  8. با tcpdump Packetهای مربوط به ارتباط را مشاهده کنید.

در پایان برای هر مرحله بنویسید که کدام بخش از TCP/IP را مشاهده کردید و اگر آن مرحله شکست می‌خورد، چه نوع مشکلی احتمال می‌دادید.
