OSI Model چیست؟

مدل OSI یا Open Systems Interconnection یک مدل مفهومی برای توضیح نحوه برقراری ارتباط بین سیستم‌های کامپیوتری در شبکه است.

این مدل ارتباط شبکه را به ۷ لایه تقسیم می‌کند. هر لایه مسئول مجموعه مشخصی از وظایف است و با لایه‌های مجاور خود ارتباط دارد.

نکته مهم این است که OSI یک مدل مفهومی است؛ یعنی در دنیای واقعی الزاماً هفت نرم‌افزار یا هفت سرویس کاملاً جداگانه نداریم. بسیاری از Protocolها و قابلیت‌های واقعی بین چند لایه قرار می‌گیرند.

نکته مهم: هدف اصلی OSI حفظ کردن شماره لایه‌ها نیست. هدف این است که وقتی یک مشکل شبکه اتفاق می‌افتد بتوانید بگویید: «این مشکل احتمالاً در کدام بخش از مسیر ارتباط قرار دارد؟»

چرا OSI مهم است؟

فرض کنید یک برنامه روی Linux نمی‌تواند به یک Web Server متصل شود. اگر فقط بگوییم «Network مشکل دارد»، تقریباً هیچ اطلاعات مفیدی نداریم.

اما اگر از مدل OSI استفاده کنیم، مشکل را مرحله‌به‌مرحله محدود می‌کنیم:

  • آیا کارت شبکه و Link فعال است؟
  • آیا Interface دارای IP است؟
  • آیا Route مناسب وجود دارد؟
  • آیا مقصد Reachable است؟
  • آیا Port موردنظر باز است؟
  • آیا TLS Handshake انجام می‌شود؟
  • آیا Application پاسخ مناسبی می‌دهد؟

این نوع تفکر باعث می‌شود Troubleshooting به جای حدس زدن، به یک فرآیند منطقی تبدیل شود.

هفت لایه در یک نگاه

Layer نام مفهوم اصلی PDU
7 Application سرویس‌های شبکه برای Application Data
6 Presentation Encoding / Encryption / Compression Data
5 Session مدیریت Session Data
4 Transport TCP / UDP / Ports Segment / Datagram
3 Network IP / Routing Packet
2 Data Link MAC / Ethernet / VLAN Frame
1 Physical Signal / Cable / Radio Bits

Layer 1 — Physical

LAYER 1

Physical Layer

این پایین‌ترین لایه OSI است و با انتقال واقعی Bitها از یک نقطه به نقطه دیگر سروکار دارد.

در این لایه با مواردی مانند کابل، Fiber، Radio Signal، Connector، Transceiver، Link Speed و Duplex روبه‌رو می‌شویم.

Bits Cable Fiber Radio Signal Speed Duplex

نمونه مشکلات Layer 1

  • کابل قطع شده است.
  • Interface خاموش است.
  • Switch Port Down است.
  • Fiber یا Transceiver مشکل دارد.
  • Speed یا Duplex به شکل نامناسب Negotiation شده است.
  • Wireless Signal ضعیف است.

بررسی در Linux

Ubuntu 
ip link

اگر Interface به شکل DOWN باشد، قبل از بررسی IP و Routing باید وضعیت Interface را بررسی کنیم.

Ubuntu 
ip link show eth0

در محیط‌های Server می‌توان از ابزارهایی مانند ethtool نیز برای مشاهده اطلاعات Link استفاده کرد.

Ubuntu 
sudo ethtool eth0

Layer 2 — Data Link

LAYER 2

Data Link Layer

Layer 2 مسئول ارتباط در سطح شبکه محلی است. مفاهیمی مانند Ethernet Frame، MAC Address، Switch و VLAN در این سطح اهمیت زیادی دارند.

MAC Address Ethernet Frame Switch VLAN ARP

MAC Address چیست؟

MAC Address یک شناسه سخت‌افزاری یا Link-Layer برای Interface شبکه است. مثلاً:

Example 
3c:52:82:ab:12:ef

Switch معمولاً MAC Addressهای دیده‌شده را در MAC Address Table خود یاد می‌گیرد و بر اساس آن‌ها Frameها را Forward می‌کند.

مشکلات رایج Layer 2

  • VLAN اشتباه
  • Switch Port اشتباه
  • MAC Learning مشکل‌دار
  • ARP Resolution مشکل‌دار
  • Broadcast Domain اشتباه
  • Interface بدون Link

بررسی MAC در Linux

Ubuntu 
ip link show

بررسی Neighbor Table

Ubuntu 
ip neigh

خروجی ip neigh اطلاعاتی درباره ارتباط IPهای محلی با MAC Address ارائه می‌دهد و برای Troubleshooting در شبکه‌های Ethernet بسیار مفید است.

Layer 3 — Network

LAYER 3

Network Layer

در Layer 3 تمرکز از شبکه محلی به ارتباط بین Networkهای مختلف منتقل می‌شود.

مهم‌ترین مفاهیم این لایه عبارت‌اند از:

  • IPv4
  • IPv6
  • Subnet
  • Routing
  • Router
  • Default Gateway
IP Packet Router Routing Table Subnet Gateway

IP Address چه کاری انجام می‌دهد؟

IP Address به سیستم کمک می‌کند مقصد را در سطح Network مشخص کند. برای مثال:

Example 
192.168.1.20

اما داشتن IP به تنهایی کافی نیست. سیستم باید بداند برای رسیدن به مقصد از کدام مسیر استفاده کند. اینجاست که Routing Table وارد می‌شود.

Routing Table

Ubuntu 
ip route

مثلاً ممکن است خروجی شامل چیزی شبیه این باشد:

Example 
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link

در این مثال:

  • شبکه 192.168.1.0/24 مستقیماً از طریق eth0 قابل دسترسی است.
  • برای مقصدهای دیگر، سیستم از Gateway با آدرس 192.168.1.1 استفاده می‌کند.

مشکلات رایج Layer 3

  • IP اشتباه
  • Subnet Mask اشتباه
  • Default Gateway اشتباه
  • Routing Table ناقص
  • Route اشتباه
  • IP Conflict
  • عدم دسترسی به شبکه مقصد

Layer 4 — Transport

LAYER 4

Transport Layer

Layer 4 مسئول ارتباط End-to-End بین Applicationهاست. در این لایه مفاهیمی مانند TCP، UDP و Port اهمیت دارند.

TCP UDP Port Segment Datagram Connection

TCP

TCP یک Connection-Oriented Protocol است. قبل از انتقال داده، Connection ایجاد می‌شود و TCP قابلیت‌هایی مانند Ordering، Reliability و Retransmission را فراهم می‌کند.

یکی از مفاهیم مهم TCP، سه مرحله Handshake است:

TCP 3-Way Handshake 
Client                         Server

   SYN ------------------------>

       <---------------------- SYN-ACK

   ACK ------------------------>

        Connection Established

UDP

UDP ساختار ساده‌تری دارد و برخلاف TCP یک Connection قابل‌اعتماد مشابه TCP ایجاد نمی‌کند.

به همین دلیل برای سناریوهایی مانند DNS، بعضی Streamingها و برخی Applicationهای Real-Time بسیار رایج است.

Port چیست؟

Port به سیستم عامل کمک می‌کند بداند داده دریافتی باید به کدام Application تحویل داده شود.

مثلاً:

  • HTTP → 80
  • HTTPS → 443
  • SSH → 22
  • DNS → 53

بررسی Portهای Listening

Ubuntu 
ss -lntup

مشکل مهم Layer 4

فرض کنید Server کاملاً روشن است و Ping نیز جواب می‌دهد، اما:

Ubuntu 
curl http://192.168.1.10:8080

خطای Connection Refused دریافت می‌کنیم.

در چنین شرایطی باید بررسی کنیم آیا Application واقعاً روی Port موردنظر Listening است یا Firewall ارتباط را مسدود کرده است.

Layer 5 — Session

LAYER 5

Session Layer

Session Layer در مدل OSI مسئول مفاهیمی مانند ایجاد، مدیریت و پایان Sessionهای منطقی بین سیستم‌هاست.

در Stackهای مدرن، وظایف این لایه معمولاً به شکل مستقل و جداگانه وجود ندارند و ممکن است بین Application، Libraries و Protocolهای دیگر تقسیم شده باشند.

Session State Dialog Connection Management

چرا این Layer در Troubleshooting مهم است؟

گاهی Network کاملاً سالم است و TCP Connection نیز برقرار می‌شود، اما Application Session ایجاد نمی‌شود یا Session بعد از مدتی قطع می‌شود.

در چنین شرایطی باید State مربوط به Application را نیز بررسی کرد.

Layer 6 — Presentation

LAYER 6

Presentation Layer

Presentation Layer وظایفی مانند تبدیل Format داده، Encoding، Compression و Encryption را در مدل مفهومی OSI توضیح می‌دهد.

Encoding Serialization Compression Encryption Data Format

مثال TLS

وقتی با HTTPS ارتباط برقرار می‌کنیم، علاوه بر TCP باید فرآیندهای مربوط به TLS نیز انجام شوند.

Ubuntu 
curl -v https://example.com

اگر TCP Connection برقرار شود ولی TLS Handshake شکست بخورد، مشکل لزوماً در Routing یا Port نیست. ممکن است Certificate، TLS Version، SNI یا تنظیمات رمزنگاری مشکل داشته باشد.

Layer 7 — Application

LAYER 7

Application Layer

Application Layer جایی است که Applicationهای شبکه با سرویس‌های قابل استفاده توسط برنامه‌ها سروکار دارند.

HTTP HTTPS DNS SSH SMTP FTP

HTTP Example

HTTP 
GET / HTTP/1.1
Host: example.com

در اینجا Application Layer به شکل واضح قابل مشاهده است: Application درخواست HTTP ایجاد می‌کند و Server پاسخ HTTP برمی‌گرداند.

DNS

Ubuntu 
dig example.com

DNS نامی مانند example.com را به IP Address تبدیل می‌کند. این فرآیند برای بسیاری از Applicationهای شبکه حیاتی است.

PDU در هر Layer

یکی از مفاهیم مهم برای درک OSI، مفهوم Protocol Data Unit یا PDU است.

Layer PDU نمونه
Layer 7 Data HTTP Request
Layer 6 Data Encrypted Data
Layer 5 Data Session Data
Layer 4 Segment / Datagram TCP / UDP
Layer 3 Packet IP Packet
Layer 2 Frame Ethernet Frame
Layer 1 Bits Electrical / Optical / Radio Signal

Encapsulation و Decapsulation

یکی از بهترین روش‌ها برای درک OSI این است که ببینیم وقتی یک Application داده‌ای ارسال می‌کند چه اتفاقی می‌افتد.

Encapsulation

فرض کنید یک Browser می‌خواهد به یک Web Server متصل شود. داده از Layer 7 به سمت Layer 1 حرکت می‌کند. هر Layer اطلاعات مربوط به خودش را اضافه می‌کند.

Concept 
Application Data
       ↓
TCP Header + Data
       ↓
IP Header + TCP Segment
       ↓
Ethernet Header + IP Packet + Trailer
       ↓
Bits
       ↓
Network

Decapsulation

در سمت Server فرآیند برعکس اتفاق می‌افتد.

Concept 
Bits
  ↓
Ethernet Frame
  ↓
IP Packet
  ↓
TCP Segment
  ↓
Application Data
مدل ذهنی مهم: فرستنده معمولاً از بالا به پایین Encapsulate می‌کند و گیرنده از پایین به بالا Decapsulate می‌کند.

مثال واقعی: وقتی curl اجرا می‌کنیم چه اتفاقی می‌افتد؟

یکی از بهترین تمرین‌ها این است که یک دستور ساده را از دید OSI بررسی کنیم.

Ubuntu 
curl https://example.com

مرحله ۱ — DNS

سیستم باید نام example.com را به IP تبدیل کند.

Ubuntu 
dig example.com

مرحله ۲ — Routing

سیستم بررسی می‌کند مقصد از چه Routeای قابل دسترسی است.

Ubuntu 
ip route

مرحله ۳ — Layer 2

اگر مقصد در شبکه محلی نباشد، سیستم معمولاً Frame را به سمت Default Gateway ارسال می‌کند و برای یافتن MAC مربوط به Gateway به Neighbor/ARP Resolution نیاز دارد.

Ubuntu 
ip neigh

مرحله ۴ — TCP

برای HTTPS معمولاً TCP Connection به Port 443 ایجاد می‌شود.

Ubuntu 
ss -tn

مرحله ۵ — TLS

بعد از ایجاد TCP Connection، TLS Handshake انجام می‌شود.

مرحله ۶ — HTTP

در نهایت HTTP Request ارسال می‌شود و Server پاسخ می‌دهد.

Ubuntu 
curl -I https://example.com
نتیجه: یک دستور ساده مثل curl می‌تواند چندین مرحله از Stack شبکه را درگیر کند. بنابراین وقتی curl شکست می‌خورد، نباید فوراً نتیجه بگیریم که «HTTP مشکل دارد».

OSI در برابر TCP/IP

در محیط‌های واقعی شبکه معمولاً بیشتر با مدل TCP/IP مواجه می‌شویم.

OSI TCP/IP نمونه
Application Application HTTP / DNS / SSH
Presentation Encoding / TLS / Data Format
Session Session Management
Transport Transport TCP / UDP
Network Internet IP / ICMP
Data Link Network Access Ethernet / MAC
Physical Physical Media

به همین دلیل در بسیاری از منابع، سه Layer بالایی OSI در یک Application Layer در مدل TCP/IP ترکیب می‌شوند.

OSI و Linux

یکی از مهم‌ترین مهارت‌ها برای DevOps این است که مدل مفهومی OSI را به دستورات واقعی Linux متصل کنیم.

موضوع دستور ارتباط با OSI
Interface ip link Layer 1 / 2
MAC ip link Layer 2
Neighbor ip neigh Layer 2
IP ip addr Layer 3
Routing ip route Layer 3
Ports ss Layer 4
DNS dig Layer 7
HTTP curl Layer 7
Packets tcpdump Multiple Layers

روش Troubleshooting بر اساس OSI

یکی از کاربردهای اصلی OSI این است که هنگام Incident بتوانیم از پایین‌ترین بخش‌های ارتباط شروع کنیم و مرحله‌به‌مرحله جلو برویم.

Step 1 — بررسی Interface

Ubuntu 
ip link

Step 2 — بررسی IP

Ubuntu 
ip addr

Step 3 — بررسی Route

Ubuntu 
ip route

Step 4 — بررسی Gateway

Ubuntu 
ping -c 4 192.168.1.1

Step 5 — بررسی Internet Connectivity

Ubuntu 
ping -c 4 1.1.1.1

Step 6 — بررسی DNS

Ubuntu 
dig example.com

Step 7 — بررسی Port

Ubuntu 
nc -vz example.com 443

Step 8 — بررسی Application

Ubuntu 
curl -v https://example.com
روش حرفه‌ای: به جای اجرای تصادفی چندین دستور، ابتدا مشخص کنید در کدام مرحله ارتباط شکست می‌خورد و سپس فقط همان بخش را عمیق‌تر بررسی کنید.

سناریوهای واقعی Troubleshooting

سناریو ۱ — Ping به Gateway جواب نمی‌دهد

اگر سیستم نمی‌تواند Default Gateway را Ping کند، ابتدا باید Interface، IP، Subnet و وضعیت Layer 2 را بررسی کنیم.

Ubuntu 
ip link
ip addr
ip neigh
ip route

در این مرحله هنوز بررسی HTTP یا DNS معمولاً اولویت ندارد؛ چون ارتباط پایه شبکه هنوز برقرار نشده است.

سناریو ۲ — Ping به IP کار می‌کند ولی Domain کار نمی‌کند

فرض کنید:

Ubuntu 
ping -c 4 1.1.1.1

موفق است اما:

Ubuntu 
ping -c 4 example.com

شکست می‌خورد.

یکی از مظنون‌های اصلی DNS است.

Ubuntu 
resolvectl status
dig example.com

سناریو ۳ — Ping کار می‌کند ولی Port بسته است

ممکن است:

Ubuntu 
ping -c 4 192.168.1.10

موفق باشد اما:

Ubuntu 
nc -vz 192.168.1.10 8080

شکست بخورد.

در این حالت باید Layer 4 و سپس Application را بررسی کنیم.

  • آیا Application روی Port 8080 Listening است؟
  • آیا Firewall ارتباط را Block می‌کند؟
  • آیا Application روی IP صحیح Bind شده است؟
Server 
ss -lntp

سناریو ۴ — TCP وصل می‌شود ولی HTTPS خطا دارد

در این حالت ممکن است Network و TCP سالم باشند اما TLS یا Application مشکل داشته باشد.

Ubuntu 
nc -vz example.com 443
curl -v https://example.com

اگر Port 443 قابل دسترسی باشد ولی TLS Handshake یا Certificate Validation شکست بخورد، باید سراغ جزئیات TLS برویم.

🔬 Advanced Lab — مشاهده Packet با tcpdump

برای اینکه OSI فقط یک مفهوم تئوری باقی نماند، می‌توانیم Packetهای واقعی را با tcpdump مشاهده کنیم.

شروع Capture

Ubuntu 
sudo tcpdump -i any

حالا در Terminal دیگری اجرا کنید:

Ubuntu 
curl -I https://example.com

در Capture می‌توانید نشانه‌هایی از ارتباطات مختلف را مشاهده کنید. برای مثال TCP Traffic، IPها و Portها.

فیلتر TCP Port 443

Ubuntu 
sudo tcpdump -i any tcp port 443

فیلتر Host

Ubuntu 
sudo tcpdump -i any host 1.1.1.1
هشدار: Packet Capture می‌تواند اطلاعات حساس را نمایش دهد. در محیط Production فقط در محدوده‌ای که مجاز به بررسی آن هستید Capture انجام دهید.

ارتباط OSI با DevOps

در DevOps تقریباً هر تکنولوژی مهمی به Networking وابسته است. بنابراین OSI فقط یک مبحث آموزشی برای Network Engineers نیست.

Docker

Docker Containerها برای ارتباط با یکدیگر از Network Namespace، Virtual Ethernet، Bridge و IP استفاده می‌کنند.

وقتی یک Container نمی‌تواند Container دیگری را پیدا کند، مفاهیم Layer 2، Layer 3، DNS و Portها بسیار مهم می‌شوند.

Kubernetes

در Kubernetes، Service، Pod، DNS، Routing و Network Policy همگی نیازمند درک درست Networking هستند.

Cloud

در Cloud مفاهیمی مانند:

  • VPC / VNet
  • Subnet
  • Route Table
  • Security Group
  • Load Balancer
  • Private IP
  • Public IP

مستقیماً با مفاهیم Networking مرتبط هستند.

Monitoring

در ابزارهایی مانند Zabbix و Grafana نیز بسیاری از مشکلات Monitoring ریشه شبکه‌ای دارند.

برای مثال:

  • Zabbix Agent قابل دسترسی نیست.
  • SNMP پاسخ نمی‌دهد.
  • HTTP Endpoint Down است.
  • Database Connection برقرار نمی‌شود.
  • Exporter روی Port موردنظر Listening نیست.

در چنین شرایطی مدل OSI می‌تواند مسیر Troubleshooting را مشخص کند.

📋 OSI Troubleshooting Cheat Sheet

Layer تمرکز دستورهای مفید نمونه مشکل
L1 Physical / Link ip link Link Down
L2 MAC / Ethernet ip neigh ARP / VLAN
L3 IP / Routing ip addr / ip route Wrong Route
L4 TCP / UDP / Port ss / nc Port Closed
L5 Session Application Logs Session Drop
L6 TLS / Encoding curl -v TLS Error
L7 Application curl / dig HTTP / DNS Error

🧠 تمرین و سؤال

تمرین ۱

اگر Interface سیستم Down باشد، از کدام Layer شروع به بررسی می‌کنید؟

تمرین ۲

اگر IP Address قابل Ping باشد ولی TCP Port 8080 قابل اتصال نباشد، کدام Layer را باید بررسی کنید؟

تمرین ۳

اگر ping 1.1.1.1 موفق باشد ولی ping example.com شکست بخورد، کدام بخش را بررسی می‌کنید؟

تمرین ۴

اگر TCP Connection روی Port 443 برقرار شود ولی curl https://example.com خطای TLS بدهد، آیا باید Routing را اولین مظنون بدانیم؟

تمرین ۵

برای هر دستور زیر Layer اصلی مرتبط را مشخص کنید:

  • ip addr
  • ip route
  • ss -lntup
  • dig example.com
  • curl -v https://example.com
  • tcpdump

🎯 چه چیزی یاد گرفتیم؟

  • مدل OSI یک مدل مفهومی برای تقسیم فرآیند ارتباط شبکه به هفت Layer است.
  • Layer 1 با انتقال فیزیکی Bitها سروکار دارد.
  • Layer 2 مفاهیمی مانند Ethernet، MAC و Frame را پوشش می‌دهد.
  • Layer 3 شامل IP و Routing است.
  • Layer 4 شامل TCP، UDP و Portهاست.
  • Layerهای 5 و 6 مفاهیم Session، Data Representation و Encryption را مدل می‌کنند.
  • Layer 7 با Protocolهای Application مانند HTTP، DNS و SSH سروکار دارد.
  • Encapsulation و Decapsulation توضیح می‌دهند داده چگونه در Stack شبکه حرکت می‌کند.
  • دستورهای Linux به ما اجازه می‌دهند بسیاری از این مفاهیم را روی سیستم واقعی مشاهده کنیم.
  • OSI یک ابزار ذهنی بسیار مفید برای Troubleshooting سیستم‌های DevOps است.
نکته DevOps: یک DevOps Engineer لازم نیست تمام جزئیات Networking را مانند یک Network Engineer متخصص حفظ کند؛ اما باید بتواند وقتی یک سرویس Down شد، مشکل را به بخش‌های قابل بررسی تقسیم کند. اگر بدانید مشکل در Interface، Routing، TCP، TLS یا Application است، به جای حدس زدن می‌توانید با ابزار مناسب همان بخش را بررسی کنید.
